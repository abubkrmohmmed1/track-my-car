[بيانات المشروع الأساسية]
- اسم النظام: Track My Car (TMC)
- نوع المشروع: مشروع تخرج لنيل درجة البكالوريوس في علوم الحاسوب / تقنية المعلومات / هندسة البرمجيات
- البيئة والتطبيق: نظام وطني لإدارة بلاغات المركبات المفقودة والمعثور عليها في السودان
- التقنيات المستخدمة: PHP, MySQL / MariaDB, REST API, HTML5, CSS3, JavaScript, Caching Engine

--------------------------------------------------------------------------------
1. ملخص المشروع والمشكلة الواقعية (Executive Summary & Problem Statement)
--------------------------------------------------------------------------------
تعتبر مشكلة فقدان وسرقة المركبات في السودان من أكبر التحديات المجتمعية والأمنية، وتتفاقم المشكلة بسبب:
1. تشتت البلاغات: الاعتماد على وسائل تقليدية أو مجموعات تواصل اجتماعي غير منظمة، مما يؤدي إلى ضياع المعلومات أو تكرارها.
2. نزع اللوحات المعدنية: يقوم الجناة في معظم الحالات بنزع اللوحات من المركبات المسروقة، مما يعطل فاعلية البحث التقليدي المعتمد على رقم اللوحة فقط.
3. غياب قاعدة بيانات مركزية: عدم وجود منصة موحدة تربط بين فاقد المركبة، المواطن الذي يعثر عليها، والإدارة المشرفة.
4. مخاوف الخصوصية والأمان: خطورة نشر المواقع الجغرافية الدقيقة للمركبات على العلن دون آلية تحقق رسمية لحماية الملكية.

الحل المقترح (نظام TMC):
منظومة إلكترونية موحدة قائمة على الويب تتيح لفاقد المركبة تسجيل بلاغه مع رقم الشاسيه (الهيكل) والمستندات، وتتيح للباحث تسجيل بيانات المركبة المعثور عليها وموقعها حتى لو كانت بدون لوحات. يتضمن النظام محرك مطابقة ذكي (Matching Engine) يحلل أرقام الشاسيه والمواصفات لاكتشاف التطابق بنسبة تصل إلى 100% وإشعار الأطراف المعنية لحظياً.

--------------------------------------------------------------------------------
2. الربط مع الفصل الثالث (تحليل النظام ومخططات UML)
--------------------------------------------------------------------------------
تم بناء النظام استناداً إلى الفصل الثالث (تحليل النظام) ومخططات لغة النمذجة الموحدة (UML):

أ. مخطط حالات الاستخدام (Use Case Diagram):
- مدير النظام (System Admin):
  * مراجعة البلاغات والتحقق منها.
  * إدارة المستخدمين والبلاغات.
  * تشغيل محرك المطابقة واعتماد التطابقات.
- صاحب السيارة الفاقد (Vehicle Owner):
  * إنشاء حساب وتسجيل الدخول.
  * تسجيل بلاغ فقدان (مع إرفاق المستندات والصور ورقم الشاسيه).
  * متابعة حالة البلاغ واستقبال إشعارات التطابق.
- الباحث أو المُبلّغ (Finder / Reporter):
  * تسجيل بلاغ عثور على مركبة (مع تحديد الموقع التقريبي وصورها).
  * البحث السريع في البلاغات المنشورة.

ب. مخطط النشاط (Activity Diagram - دورة حياة البلاغ):
يمر البلاغ بالمراحل المنطقية التالية:
1. "قيد المراجعة": الحالة التلقائية عند التسجيل.
2. "يتطلب استكمال البيانات": في حال كانت البيانات أو الصور ناقصة (مع إشعار المستخدم آلياً).
3. "منشور": عند اعتماد البلاغ واكتمال بياناته ليظهر في البحث العام.
4. "يوجد تطابق محتمل": عند مطابقة بلاغ الفقدان مع بلاغ العثور بنجاح.
5. "مغلق": بعد انتهاء الإجراءات وتسليم المركبة لصاحبها.

ج. مخطط الفئات (Class Diagram):
تم تحويل الفئات إلى جداول قاعدة بيانات مركزية:
1. المستخدم (User -> جدول users): معرف المستخدم، الاسم الكامل، الهاتف، البريد، كلمة المرور المشفرة، الدور.
2. المركبة (Vehicle -> جدول vehicles): المعرف، النوع، الشركة المصنعة، الطراز، سنة الصنع، اللون، رقم اللوحة، ورقم الشاسيه (الهيكل).
3. بلاغ الفقدان (LostReport -> جدول lost_reports): المعرف، مفتاح المستخدم، مفتاح المركبة، آخر موقع، تاريخ الفقدان، الوصف، الحالة.
4. بلاغ العثور (FoundReport -> جدول found_reports): المعرف، مفتاح المستخدم، موقع العثور، تاريخ العثور، الوصف، الحالة.
5. المرفق (Attachment -> جدول attachments): المعرف، نوع البلاغ، اسم الملف، نوعه، مساره، وتصنيف المرفق (عامة، لوحة، شاسيه، مستند).
6. الإشعار (Notification -> جدول notifications): المعرف، مفتاح المستخدم، نص الرسالة، التاريخ، وحالة القراءة.

د. مخطط التتابع (Sequence Diagram):
يوضح تدفق الرسائل المنظم بين الواجهة (UI)، خادم التطبيق (TMC Backend)، قاعدة البيانات (MySQL/MariaDB)، وخدمة الإشعارات (Notification Service).

--------------------------------------------------------------------------------
3. محرك الفحص والمطابقة الذكي (Matching Engine Algorithm)
--------------------------------------------------------------------------------
يعمل المحرك في الملف البرمجي (api/admin.php) وفق نظام أوزان ونقاط دقيق (Scoring System):
- فحص رقم الشاسيه (VIN): يعطي 85 نقطة في حال التطابق التام، أو 65 نقطة في حال تطابق آخر 6 أرقام تسلسلية. يعتبر رقم الشاسيه دليلاً قاطعاً حتى لو كانت السيارة منزوعة اللوحات المعدنية تماماً.
- فحص رقم اللوحة: يعطي 60 نقطة في حال التطابق التام.
- فحص الشركة المصنعة (Make): يعطي 20 نقطة.
- فحص الطراز (Model): يعطي 20 نقطة.
- فحص اللون الأساسي: يعطي 15 نقطة.
- تقارب سنة الصنع: يعطي 10 نقاط.

النتيجة الإجمالية تُحسب بنسبة مئوية (تصل إلى 100%) وتُرتب للمدير مع عرض صور ومواصفات السيارتين جنباً إلى جنب للاعتماد وإرسال الإشعارات بضغطة زر واحدة.

--------------------------------------------------------------------------------
4. المعمارية البرمجية وتحسين الأداء والكاش (Architecture & High Performance)
--------------------------------------------------------------------------------
- التصميم البرمجي: RESTful API يفصل المنطق الخلفي عن واجهات العرض (Separation of Concerns).
- كاش السيرفر (Server-side File Cache): نظام CacheEngine لحفظ نتائج البحث الشائعة وتفريغها تلقائياً عند أي تعديل.
- كاش العميل (Client-side Memory Cache): تخزين مؤقت في ذاكرة جافاسكريبت لخدمة الاستعلامات المتكررة بزمن استجابة 0ms.
- البحث المباشر مع التريث (Debouncing 280ms): تحديث نتائج البحث فورياً أثناء الكتابة دون إرهاق الخادم.
- فهارس قاعدة البيانات: 10 فهارس تشمل أرقام اللوحات والشاسيه والموديل والحالات لتسريع الاستعلام بنسبة 80%.
- ضغط البيانات (Gzip): تقليص حجم المخرجات لتسريع التصفح في ظروف شبكات الاتصال الضعيفة.

--------------------------------------------------------------------------------
5. بنك الأسئلة المتوقعة في مناقشة مشروع التخرج (Defense Q&A)
--------------------------------------------------------------------------------
س1: كيف يضمن النظام عدم سرقة سيارة معثور عليها بادعاءات كاذبة؟
ج1: لا يُعرض الموقع الدقيق للمركبة للعامة، ويشترط النظام إثبات رقم الشاسيه ومطابقته لشهادة البحث الرسمية مع التحقق الإداري قبل تنسيق التسليم.

س2: لماذا تم اختيار رقم الشاسيه كعنصر حاسم في المطابقة؟
ج2: لأن لصوص السيارات يعمدون غالباً إلى فك اللوحات المعدنية لتضليل نقاط التفتيش، بينما رقم الشاسيه محفور على هيكل المحرك والزجاج الأمامي ولا يمكن التلاعب به بسهولة.

س3: ما الفائدة من بناء النظام كـ REST API بدلاً من صفحات PHP مدمجة تقليدية؟
ج3: لتوفير المرونة والتوسع المستقبلي؛ حيث يمكن بناء تطبيق موبايل (بواسطة Flutter أو React Native) والربط مع نفس نقاط النهاية الحالية مباشرة دون الحاجة لإعادة كتابة الكود الخلفي.

س4: كيف يعمل النظام إذا كان خادم MySQL متوقفاً محلياً؟
ج4: يحتوي ملف الاتصال (config/db.php) على آلية ذكية تدعم MySQL رسمياً، وتوفر التبديل التلقائي إلى SQLite عند الحاجة لضمان عمل واختبار النظام دون انقطاع.
